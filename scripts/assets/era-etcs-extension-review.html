The CCS/TMS extension, checked against ERA Ontology v4.0.0

The ext-ccstms branch adds 1,177 ETCS, TMS and infrastructure-engineering terms to the era: namespace. This review checks the branch, its last release v1.1.1 and its SKOS vocabularies against the core release v4.0.0, ERA's extension governance framework, the ERA principles and live RINF data.

01Verdict

NOT READY

The extension cannot be aligned with v4.0.0 as it stands. On its own it is consistent, well documented in purpose and largely clean against live RINF data. Merged with v4.0.0, it breaks in three ways.

Data that matches either side makes the merged ontology inconsistent. The branch and v4.0.0 define era:x, era:y, era:z and era:offset separately, with ranges no literal can satisfy at once. HermiT proves this with a single value, and the control runs beside it stay consistent.

Three IRIs are both object and datatype properties. OWL 2 DL forbids this.

The branch is a copy of core v3.3.3, not a module on top of the core. It carries the same ontology IRI and calls itself "ERA Ontology v3.3.3". v4.0.0 has moved on from that base.

Behind these: the only release, v1.1.1, makes 6,480 live RINF operational points inconsistent, 302 released terms were dropped without deprecation, and the hosted validator applies shapes (v1.3, v1.4.0) that the repository does not hold.

Re-checked against v4.0.0. The review was first measured on 22 November against the candidate release v4.0.0-rc.5. ERA tagged v4.0.0 on 23 November. Between the two tags, ontology.ttl changes only its owl:versionInfo and owl:versionIRI (47,693 triples each), all 425 era-skos/ files are byte-identical, and era-shacl/ is untouched. The extension governance framework changes only one URL, and the ext-ccstms branch has not moved. Every term check and all 16 reasoner runs were repeated with v4.0.0 as the target, with the same results. The findings therefore apply to v4.0.0 unchanged.

04Findings

Each finding gives its evidence, why it matters and the action to take. "Confirmed" means it was measured or proved by a reasoner. "Design" means it is a recommendation where reasonable people could choose otherwise.

Blockers

B1BLOCKERFour properties get ranges that no value can satisfy once merged with v4.0.0 confirmed

Evidence. The branch head and v4.0.0 both define era:x, era:y and era:z. The head uses them for map projections, with range xsd:double; v4.0.0 uses them for coach-layout grids, with range xsd:int. era:offset is xsd:double on the head and xsd:integer in v4.0.0. In OWL 2 the value spaces of xsd:double and of the integer types are disjoint, and two rdfs:range axioms are read together, so no literal can be a value. HermiT shows this with one individual:

RunResult
v4.0.0 + ex:a era:x "3"^^xsd:int (control)CONSISTENT
v4.0.0 + extension delta + the same xsd:int valueINCONSISTENT
branch head + ex:a era:x "1.5"^^xsd:double (control)CONSISTENT
v4.0.0 + extension delta + the same xsd:double valueINCONSISTENT
v4.0.0 + ex:a era:offset "2"^^xsd:integer (control)CONSISTENT
v4.0.0 + extension delta + the same valueINCONSISTENT
 
# v4.0.0
era:x a owl:DatatypeProperty ; rdfs:range xsd:int ;
      rdfs:domain [ owl:unionOf ( era:CoachLayoutGridSize era:GridPosition … ) ] .
# ext-ccstms head
era:x a owl:DatatypeProperty ; rdfs:range xsd:double ;
      rdfs:domain [ owl:unionOf ( era:FunctionalElementProjection era:LinearElementCoordinate ) ] .
# merged: every value of era:x must be an xsd:int and an xsd:double. None is.

Impact. Any data that uses these properties, whether coach layouts that conform to v4.0.0 or map data that conforms to the extension, makes a reasoner reject the merged ontology. The two meanings are unrelated: a seat-grid column has nothing to do with a projected easting. y and z have the same ranges as x; they were not run separately. Four core LRS properties (offsetFromOrigin, startOffsetFromOrigin, endOffsetFromOrigin, lengthOfNetLinearElement) have the same pattern on a naive file merge: still xsd:double on the branch, xsd:decimal in v4.0.0. Rebasing (B3) removes those four. The other four need new names.

Give the extension's terms their own IRIs, for example era:projectedX, or reuse GeoSPARQL geometry. Never mint a term whose IRI the target core release already defines. Add an IRI-collision check against the target tag to CI (S2).

B2BLOCKERThree IRIs are both object and datatype properties confirmed

Evidence.

  • era:gsmrConstraintsOperateOnlyInCircuitSwitch and era:etcsBaselineIncompleteCompatibility are datatype properties in v3.3.3 and v4.0.0, with range xsd:string. The head adds rdf:type owl:ObjectProperty to both, keeping owl:DatatypeProperty and the xsd:string range.
  • era:accuracy is a new datatype property on the head (xsd:double, domain era:OffsetAccuracy). v4.0.0 defines it as an object property ranging over skos:Concept, with domain GeoCoordinateDef ⊔ GeoCoordinateType.
  • Release v1.1.1 had four such conflicts: accuracy, gsmrConstraintsOperateOnlyInCircuitSwitch, vehiclePantographHead and warning.
  • Owlready2 reported each IRI while loading ("belongs to more than one entity types … trying to fix it").

Impact. OWL 2 DL does not allow one IRI as both an object and a data property. DL tools then reject the ontology, or silently "repair" it in tool-specific ways, so different consumers see different ontologies. An object-property declaration with a literal range is also self-contradictory on its own.

Remove the two extra owl:ObjectProperty types. If a coded value is meant, add a new object property and deprecate the string one (P4, P8). Rename the extension's accuracy, for example era:offsetAccuracyValue.

B3BLOCKERThe branch is a fork of core v3.3.3, published under the core's IRI and version confirmed

Evidence. The head's ontology.ttl is the whole core v3.3.3 with 8,020 triples added. The header is still the core's: ontology IRI http://data.europa.eu/949/, owl:versionInfo "v3.3.3", owl:versionIRI …/-/releases/v3.3.3, owl:priorVersion …/v3.3.2. Release v1.1.1 uses the same ontology IRI with owl:versionInfo "v1.1.1". No document states which core version the extension builds on. v4.0.0 comes after v3.3.4 and has changed core terms the branch keeps: four LRS offsets went from xsd:double to xsd:decimal, and v4.0.0 added its own x, offset, startDate and Platform.

Impact. Two different files claim to be "ERA Ontology v3.3.3" and neither says which one is meant. The extension cannot be loaded as a module on top of v4.0.0, or later on v4.0.0. Every core release then means a three-way merge by hand. The governance framework allows its own namespace, and at least asks for a separable unit.

# illustrative module header: own IRI and version, importing the core release it extends
<http://data.europa.eu/949/ext/ccstms> a owl:Ontology ;
    owl:versionInfo "v1.2.0" ;
    owl:imports <https://gitlab.com/era-europa-eu/public/interoperable-data-programme/era-ontology/era-ontology/-/releases/v4.0.0> ;
    dct:license <http://data.europa.eu/eli/dec_impl/2017/863/oj> .

Rebase the branch on v4.0.0. Split the extension into its own file with its own ontology IRI and version, importing the core version IRI it extends. Keep the core's ontology.ttl byte-identical to the tag. See also S1.

Major

M1MAJORRelease v1.1.1 makes live RINF data inconsistent; the fix exists only on the branch head confirmed

Evidence. Release v1.1.1 declares owl:FunctionalProperty on 14 core properties. It also adds maxCardinality 1 on era:opName for era:OperationalPoint. In rinf-plus, 6,480 operational points have more than one name, many of them bilingual, for example operationalPoint/ae4b44fc65 "Riksgräns Haparanda - Tornio | Tornio-raja". HermiT on v4.0.0 plus that one point is consistent. Adding the v1.1.1 extension makes it inconsistent. Four more of the 14 properties have several values on live subjects:

  • contactStripMaterial: 51,154 subjects
  • gaugingCheckLocation: 4,737 subjects
  • trainDetectionSystemSpecificCheck: 1,126 subjects
  • localRulesOrRestrictionsDoc: 550 subjects

gaugingCheckLocation is a datatype property, so its distinct strings are inconsistent in the same way as opName. The other three are object properties: they don't make the data inconsistent, but a reasoner concludes that the distinct concepts or documents are one individual (owl:sameAs). A further 23 sections of line break the release's qualifiedCardinality 1 on era:nationalLine.

Impact. Anyone who loads the published extension with RINF, its main companion dataset, gets an inconsistent graph or merged concepts. The head no longer declares these: the head plus the same point is consistent, and the head's own new restrictions have no live violations. But no release carries the fix.

Cut a new release from the rebased head and mark v1.1.1 as superseded in the releases folder. Keep functional and cardinality constraints that RINF publishers break out of OWL: they belong in SHACL (m3).

M2MAJORShared IRIs with different domains and ranges: the merge infers wrong types confirmed

Evidence. RDFS reads several rdfs:domain or rdfs:range axioms on one property as an intersection, so each pair below makes every use infer both sides.

The head also widens the domain of three core properties. It replaces a named class with a union:

  • era:etcsMVersion: ETCS becomes BaliseGroup ⊔ ETCS ⊔ ETCSTrackToTrainPacket_2 ⊔ ETCSTrackToTrainRM_32 ⊔ SystemVersion
  • era:rbcPhone: RadioBlockCenter becomes the union with three track-to-train packets
  • era:onLinearElement: gains SegmentProfile

On a merge, v4.0.0's narrower domain survives alongside the union, so the widening has no effect except where v4.0.0's axiom is removed. That is a core change.

Impact. A TAF wagon-status message would be inferred to be an ATO event estimation, a train-unit identifier a composite identifier, and so on. No error is raised; queries and classifications are simply wrong. Changing a core domain is a "more complex" change under P4 and needs the core's agreement.

For each of the 13 IRIs, either reuse v4.0.0's term with v4.0.0's semantics or mint an extension-specific IRI. Propose the three domain widenings to the core as change requests, rather than carrying them on the branch.

M3MAJORSUBSET-026 national values duplicate regulated RINF parameters confirmed

Evidence. The head adds 11 snake_case properties for ETCS national values that v4.0.0 already has in camelCase, each with an era:rinfIndex (track parameters 1.1.1.3.2.16.x and 1.2.1.1.1.16.x):

  • d_nvroll duplicates dNvroll (RINF 1.1.1.3.2.16.1). The same holds for d_nvovtrp, d_nvpotrp, m_nvderun, q_nvdriver_adhes, q_nvemrrls, q_nvsbtsmperm, t_nvcontact, t_nvovtrp, v_nvallowovtrp and v_nvsupovtrp.
  • Two of them also differ in kind: q_nvdriver_adhes and q_nvemrrls are datatype properties on the head but coded object properties in v4.0.0, ranging over skos:Concept.
  • Ten more new terms differ from an v4.0.0 term only by case, as property/class pairs: Controller/controller, switch/Switch, operationalPoint/OperationalPoint and others.

Impact. One SUBSET-026 variable gets two IRIs, so RINF data and CCS/TMS data on the same national values never join. The governance framework keeps extensions to use cases outside the regulated scope, and RINF parameters are inside it.

Reuse v4.0.0's dNvroll family and drop the 11 duplicates; they are unreleased, so no deprecation is needed. Rename the property/class pairs so that names stay unique beyond case (P1).

M4MAJORReleased terms deleted, not deprecated confirmed

Evidence. 302 era: terms of release v1.1.1 (100 classes, 138 object, 63 datatype, 1 annotation property) don't appear anywhere in the head. None carries owl:deprecated or dct:isReplacedBy. Nine were renamed by case or separator only: nidC → nid_c, m_nvcontact → mNvcontact, RelativePosition → relativePosition, TrainDetector → trainDetector, and others. The ETCSPacket_* classes look replaced by ETCSTrackToTrainPacket_*, but no mapping says so. Between v1.1 and v1.1.1, 91 terms were removed and 31 added, also without deprecation. That step was announced only as "removal of unstable Equipment model".

Impact. Data, queries and validators written for a release stop matching, with no error. P4 is explicit: deprecate, never delete. Some renames also go against P1, from camelCase to snake_case.

Restore the 302 terms in the head as deprecated, each with dct:isReplacedBy where a successor exists. From now on, treat every released IRI as permanent.

M5MAJORRelease, branch head and validator are out of step; no extension shapes in the repository confirmed

Evidence.

  • Releases. The releases folder holds v1.1 and v1.1.1. The head has 531 terms that are in no release.
  • Validator. The ITB validator offers infra, eng and opp at v1.3 and v1.4.0 (aliased *_latest), and tp at v1.3. The validator user guide on the branch uses infra.v1.3 in its examples.
  • Shapes. The branch's era-shacl/ lists the same files as v4.0.0's (common, rinf, eratv, eradis, evr), and none is for extension terms. The extension document describes shapes per domain and class, such as BaliseGroupShape.ttl and HorizontalTransitionShape.ttl, that are not in the repository.

Impact. Nobody can tell which ontology version a v1.4.0 validation report checks data against, or review those shapes. Producers validate against rules that are not published with the ontology. This fails the Transparency requirement.

Publish the shapes the validator uses in era-shacl/ccstms/, versioned with the ontology release they belong to, and align the numbering of the ontology, the shapes and the validator. Every ITB validation type should name an ontology version IRI.

M6MAJORSchemes with the same IRI hold different concepts; coded properties point at missing schemes confirmed

Evidence. See section 5. 50 of the 92 schemes that both the head and v4.0.0 define differ, and 24 of those share no concept IRI at all. Three coded properties name a scheme that does not exist. Three scheme IRIs break P3.

Impact. A concept valid under one scheme file is unknown under the other with the same scheme IRI. Whichever file loads last decides what is valid. The core's SPARQL-based SKOS constraints (P8) then flag correct data.

For shared schemes, contribute missing concepts to the core scheme rather than redefining the scheme. Fix the three dangling pointers and the three P3 IRIs.

M7MAJORNo provenance metadata to tell extension terms from core terms confirmed

Evidence. Coverage of the P5 term metadata on the head's 1,177 new terms:

  • On every term: rdfs:label, rdfs:comment and dct:created.
  • rdfs:isDefinedBy: 17 terms.
  • dct:modified, vs:term_status and skos:definition: none.

The only other marker is era:ccsView. It is not a provenance marker: the head also puts it on 45 core terms (the documented example tags era:LinearElement), and 6 new terms lack it.

Impact. With one namespace and one ontology IRI, nothing machine-readable says which terms are core and which are extension. The documented plan to extract sub-ontologies, and any later merge into the core, then depends on diffing files. Without term_status, users can't tell stable terms from experimental ones, although the release notes call parts "unstable".

Add rdfs:isDefinedBy <extension ontology IRI>, vs:term_status and dct:modified to every extension term. Keep era:ccsView for use-case views only.

Minor

m1MINORNaming off principle P1: 106 classes, 328 properties confirmed

P1 asks for CamelCase, classes starting upper-case and properties lower-case, and names unique within the ontology. On the head:

  • 106 new classes are not UpperCamelCase, for example ETCSTrackToTrainPacket_131.
  • 328 new properties are snake_case, for example a_nvmaxredadh1 and d_adhesion.

v4.0.0 writes the same SUBSET-026 variables as dNvroll, so two styles now coexist. Nothing breaks, but every rename after release costs a deprecation (P4).

Rename before the first release that carries these terms. Keep the SUBSET-026 variable name in skos:notation (S3).

m2MINOR1,117 labels only repeat the identifier confirmed

For 1,117 of the 1,177 new terms, rdfs:label equals the local name apart from case and separators, for example D_Nvovtrp and LinearElement , the latter with a trailing space. Many comments are "Defines the …" restatements. Labels are what documentation, editors and the RINF/ERATV interfaces show people. This weakens the Clarity criterion.

Give human-readable labels, for example "Roll-away distance limit" for D_NVROLL, with a language tag (@en, as the P8 template shows). Move the SUBSET-026 mnemonic to skos:notation.

m3MINORApplication constraints written as OWL restrictions on core classes design

The head adds 24 restrictions to 9 core classes:

  • 8 are maxCardinality 1: seven on names, and one on Switch.reversalTime.
  • 5 are minQualifiedCardinality 1: Tunnel.tunnelTubes, Switch.foulingPoints, PlatformEdge.stopLocations, LevelCrossing.dangerPoints and NetAreaReference.includes.
  • 11 are minCardinality 0, which says nothing.

Live RINF has no violations of the maximum restrictions: 15,360 kilometric posts have a name, and none has two. Under the open-world assumption, though, the five minimum restrictions assert that every RINF tunnel has a tube and every switch a fouling point, whether or not anyone publishes one. These are completeness rules for CCS/TMS data, not facts about every tunnel.

Express them as SHACL shapes in the CCS/TMS profiles (S4), and drop the 11 vacuous restrictions.

m4MINORCore axioms changed from the extension governance

The head changes 51 core terms. It adds:

  • owl:disjointWith between era:VehicleSet and each of VehicleType, VehicleTypeConfiguration and VehicleTypeConfigParameterSet. None of these is in v4.0.0.
  • skos:altLabel on era:Switch ("Point"), mNvcontact and etcsMVersion.
  • 48 era:ccsView tags on 45 core terms.
  • The two punned types of B2.

No resource in rinf-plus carries two of the disjoint types; ERATV-KG was not checked. The disjointness may well be right, but it is a statement about ERATV classes, and the core should own it.

Raise the disjointness and the labels as core change requests. Keep the extension to additions.

m5MINORDocumentation gaps confirmed

  • Base version. No document states the core version the extension builds on. The newest dated release in the release notes is data model v1.1 (21 March 2025); nothing documents v1.1.1 or the head.
  • Governance. The "Governance and Change Management" chapter of the extension document reads "To be updated". The Approach document is "In Approval by System Pillar", and its licence statement contradicts the README (see section 3).
  • Examples. The SHACL example in the extension document is not valid Turtle. It uses xsd:minInclusive inside sh:property instead of sh:minInclusive, and it has an unclosed >. The prefix appendix prints era as <http://data.europa.eu/949>, without the trailing slash.
  • Direction. Some documents say releases are derived from the ERA vocabulary by an automated process. Others describe the JSON model in Polarion as the master, exported per release. They are not reconciled.

m6MINORRelease v1.1.1 datatypes outside the OWL 2 datatype map confirmed

Release v1.1.1 uses xsd:date as a range twice and geo:wktLiteral once. It also gives one datatype property, utcOffset, the range skos:Concept. HermiT runs only on a copy with those retyped; the core has the same xsd:date habit. The head no longer defines utcOffset.

Where OWL 2 DL tooling matters, prefer xsd:dateTime or xsd:dateTimeStamp, and declare geo:wktLiteral as rdfs:Datatype.

Suggestions

S1SUGGESTIONPackage the extension as a module, and generate the views from it design

Use one file per module, all importing the core release, as in the header in B3. Keep era: for terms the core accepts. A dedicated namespace, for example http://data.europa.eu/949/ext/ccstms/, is allowed by the framework and would make collisions like B1 impossible by construction. Generate the ccsView sub-ontologies from the module, as the documents already plan.

S2SUGGESTIONA CI gate that runs the checks of this review design

Each check below ran here in seconds to minutes:

  • IRI collisions and kind conflicts against the target core tag;
  • HermiT with one sample individual per property;
  • P1 and P5 lint;
  • scheme resolution for every era:inSkosConceptScheme;
  • a diff of released IRIs, so that a missing term fails the build unless it is deprecated;
  • the published shapes run against example data.

S3SUGGESTIONA pattern for SUBSET-026 variables design

era:nvRollawayDistance a owl:DatatypeProperty ;     # illustrative IRI, CamelCase (P1)
    rdfs:label "Roll-away distance (national value)"@en ;
    skos:notation "D_NVROLL" ;                       # the SUBSET-026 mnemonic, searchable
    rdfs:isDefinedBy <http://data.europa.eu/949/ext/ccstms> ;
    vs:term_status "unstable" .
# …or, for a variable v4.0.0 already has, reuse era:dNvroll and add nothing.

S4SUGGESTIONSHACL profiles per view, in the repository design

Express the cardinalities, mandatory properties and sh:in lists of each ccsView (INFRA, ENG, OPP, TP, …) as node shapes targeting the classes that view uses. Version them with the ontology, and publish the same files to ITB. This gives the validator a source, keeps OWL free of completeness rules (m3), and lets RINF data stay valid against the core while CCS/TMS data is checked more strictly.

06Shapes and the hosted validator

The repository holds no SHACL shapes for extension terms. The branch's era-shacl/ has the same file list as v4.0.0's. The rules that producers are actually checked against live only in the ITB validator (www.itb.ec.europa.eu/shacl/ccstms), as validation types infra, eng and opp at v1.3 and v1.4.0 and tp at v1.3. The validator user guide on the branch describes Java plug-ins for "domain-specific constraints that cannot be expressed in standard SHACL". Those constraints can't be reviewed or reproduced from the repository either.

Not reviewed here: the content of the ITB shapes (only the validator's list of types was read), and the 258 JSON Schema files in releases/v1.1.1/Schemas/. Both are worth a follow-up once they are published with an ontology version.

07What already works

  • Consistent on its own. HermiT finds the branch head consistent with no unsatisfiable class (29,058 triples, 6.6 s). It stays consistent with a real multi-name RINF operational point.
  • The head fixed the release's worst axioms. It adds no functional declarations, uses no term v4.0.0 deprecates, and its new cardinality restrictions have zero violations on live RINF.
  • Complete basic metadata. Every new term has a label, a comment and a creation date, and every coded property names its scheme (P8).
  • Purpose and scope are well argued. The documents give use cases, consumers, the static-data boundary and the "data model follows function" rule, plus documented reuse of OWL-Time, GeoSPARQL, QUDT and SKOS.
  • A real validation service exists. Producers can check data today through the web interface, REST, SOAP and an offline CLI.

08Path to alignment with v4.0.0

In order. Steps 1 to 4 clear the blockers. Steps 5 to 8 clear the major findings.

  1. Rebase the branch on v4.0.0, keeping the core file identical to the tag (B3).
  2. Split the extension into its own ontology file or files, with its own IRI and version, importing the v4.0.0 version IRI (B3, S1).
  3. Resolve the 13 shared IRIs: reuse v4.0.0's term with its semantics, or rename. Start with x, y, z, offset and accuracy (B1, M2).
  4. Remove the punned types on gsmrConstraintsOperateOnlyInCircuitSwitch and etcsBaselineIncompleteCompatibility (B2).
  5. Reuse v4.0.0's RINF national-value properties instead of the 11 snake_case copies (M3).
  6. Restore the 302 released terms as deprecated, with replacements (M4).
  7. Fix the SKOS layer: contribute to shared schemes, and fix the 3 pointers and the 3 IRIs (M6).
  8. Publish the shapes and the metadata (isDefinedBy, term_status), then cut a release whose number matches the validator's (M5, M7, M1).

Then rerun the checks of section 9. The release is ready when the collision, kind and range checks are empty and HermiT is consistent with one sample value per property.

Tools and how the checks work

  • rdflib 7.6.0 for parsing and graph diffs, and owlready2 0.48 with its bundled HermiT for reasoning.
  • HermiT runs on copies in which datatypes outside the OWL 2 map (xsd:date, rdf:langString, geo:wktLiteral) are retyped, because HermiT rejects them otherwise. The source files are not modified.
  • The "extension delta" is the head's new terms with their blank-node descriptions, the restrictions it adds to core classes, and its ground triples on changed core terms: 14,560 triples.
  • Terms are compared by IRI. "Near-duplicate" means equal names after lower-casing and dropping non-alphanumeric characters.
  • "Labels repeating the identifier" uses the same normalisation.

Live-data queries

  • Several values. For each property: SELECT (COUNT(*) AS ?n) WHERE { SELECT ?s WHERE { ?s era:<p> ?o } GROUP BY ?s HAVING (COUNT(DISTINCT ?o) > 1) }.
  • Cardinality restrictions. The same query restricted to the class.
  • Disjointness. COUNT(DISTINCT ?s) over ?s a era:A, era:B.

Limits

  • The reasoner runs use the ontologies plus single individuals, not the full RINF graph. They prove that a clash exists, not how much data it affects.
  • Disjointness was checked against rinf-plus only, not ERATV-KG.
  • "Reuse first" is assessed from the documents, not measured in the TTL.
  • Not reviewed: the ITB shapes, the JSON Schemas, and the extension's example instances.
  • The SKOS comparison is by IRI. Concepts that mean the same thing under different IRIs count as different, which is the point of M6.
